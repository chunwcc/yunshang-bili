# 直播播放器：横竖屏切换分析、改造方案与设计规格

> 目标文件：`entry/src/main/ets/pages/LivePlayerPage.ets`（1255 行，当前单布局全屏实现）
> 参考实现：`PiliPlus-maina-an/lib/pages/live_room/`（`view.dart` / `controller.dart` / `tcp/live.dart`）
> 本文只做分析与方案，**尚未修改任何代码**。

---

## 一、结论先行

「观看直播横竖屏切换有问题」不是一个原因，是三层问题叠在一起：

1. **P0 · 视频几何是 build 期快照，旋转后不会重算。**
   `videoW()/videoH()`（LivePlayerPage.ets:144-158）每次调用都去读 `display.getDefaultDisplaySync()`，但结果被当作
   **普通数字**写进 `.width()/.height()`（:936-938）。ArkUI 的局部更新只会在它依赖的状态
   （这里是 `ratioMode`）变化时重算这条属性；旋转改变的是窗口约束，不会触发它，
   所以 XComponent 停在上一次计算出的尺寸，直到用户点「比例」把 `ratioMode` 改掉才偶然修正。
   - 进入时是横屏 → 视频按 831×467vp 建立；转成竖屏后窗口只有 517vp 宽，`clip(true)` 把左右各裁掉约 157vp。
   - 进入时是竖屏 → 视频按 517×291vp 建立；转成横屏后缩在屏幕中间，四周大片黑边。
   这就是「转一下就坏了」的主要来源。

2. **P0 · 根布局只有一套「全屏视频 + 悬浮按钮」，没有竖屏/横屏两套布局。**
   `isFullscreen`（:49）初始为 `true` 且 build 里从未使用；整个 build（:931-1254）只有一层全屏 `Stack`。
   竖屏时 16:9 视频只占 291vp，剩下 540vp 全是黑屏——这不是旋转 bug，是**没有竖屏形态**。
   同时没有聊天/评论面板、没有房间信息区、没有输入栏。

3. **P0 · 弹幕与评论在数据层就完全不存在。**
   `LiveApi.ets` 里只有房间信息/画质/流地址，没有 `getDanmuInfo`、没有 WebSocket、没有 `msg/send`。
   `DanmakuController` 是**点播**实现（按 cid 分 6 分钟分段拉取 + 时间轴驱动），不能直接用于直播实时流；
   但 `DanmakuRenderer` / `DanmakuTrackManager` 可以原样复用（见 §4.7）。

另外还有 6 个次级缺陷，会在旋转时同时暴露：

| # | 缺陷 | 位置 | 表现 |
|---|---|---|---|
| 4 | 点击热区用一次性快照 | `initSwipeControl()` :695-704 只在 `aboutToAppear` 调一次；`onTU` :846-863 用 `screenH_*0.2/0.8` | 旋转后大片区域点不出控制栏（横屏窗口高 517vp，热区却按竖屏 831vp 算） |
| 5 | 安全区不刷新 | `getSafeArea()` :215-241 只取一次 | 旋转后控件钻到刘海/导航条下；日志里 TYPE_SYSTEM 从 `[0 0 2120 117]` 变 `[0 0 1320 117]`，右侧还有挖孔 `[2028 626 68 68]` |
| 6 | 无视全局旋转锁 | `applyRotationMode()` :899-914 无条件按 `rotationMode='auto'` 覆盖；`aboutToDisappear` :296 硬设 `AUTO_ROTATION` | 用户在设置里选了「锁定竖屏」，进直播间就被放开；退出后也不恢复原锁 |
| 7 | 竖屏直播源被按 16:9 处理 | `ratioMode` 默认 `'16:9'` :39；从不读 `videoSizeChange` | 9:16 的秀场/电商直播左右大片黑边，点「比例→铺满」还会拉伸变形 |
| 8 | 旋转期间背景页仍在重排 | 日志 10:00:50.429 `[HomePage] 方向变化: 竖屏`、10:00:50.433 `AceWaterFlow item size change` | 被盖住的首页 WaterFlow 跟着旋转重排，旋转瞬间掉帧；直播页自身也没有 `rotationInProgress` 降载 |
| 9 | 直播暂停后恢复会落后于直播 | `onPageHide` :302-314 / `onPageShow` :317-325 | 从暂停点继续解码，HLS 直播窗口内会累积延迟；应「回到直播边缘」而不是 resume |

## 三、根因归纳（一句话版）

> 直播页把「屏幕尺寸 / 视频比例 / 安全区 / 点击热区」都当成了**进入页面那一刻的常量**，
> 而旋转改变的是**窗口约束**这一个外部输入。没有一个「窗口尺寸 → 布局」的响应式派生链，
> 所以只要转屏，所有派生值全部失真；再加上本来就缺竖屏形态、缺弹幕评论，问题被放大成「整个页面都不对」。

## 四、解决方案

### 4.1 架构总览

```
LivePlayerPage (唯一页面)
├── @State winW / winH / safeTop / safeBottom / safeLeft / safeRight   ← onAreaChange + windowSizeChange
├── @State streamAR (w/h)                                            ← API videoWidth/Height + av.videoSizeChange
├── @State isLandscape = winW > winH
├── @State rotationInProgress
├── @State danmakuOn / chatPanelOpen / chatTab / followState
│
├── LiveRoomStore            (新) 房间信息、关注、在线人数、榜单
├── LiveDanmakuClient        (新) WSS 长连接、心跳、重连、消息分发
├── LiveChatStore            (新) 最近 300 条消息（弹幕/礼物/SC/系统），供聊天面板与弹幕层共用
├── LiveDanmakuController    (新) 复用 DanmakuRenderer + DanmakuTrackManager 的实时驱动
│
└── build()
    Stack (根, .onAreaChange)
      ├── 背景层           纯黑 / 竖屏源的封面模糊
      ├── 视频槽 (常驻)     XComponent 只在 videoSrc 变化时重建
      ├── 弹幕层            Canvas, 严格贴合「视频显示矩形」
      ├── 竖屏皮肤          buildPortrait()
      ├── 横屏皮肤          buildLandscape()
      └── 全局浮层          画质菜单 / 手势提示 / Toast / 发送弹幕面板
```

**铁律：视频槽和弹幕 Canvas 必须放在 `if (isLandscape)` 之外。**
布局分支只允许切换「皮肤」和几何参数；一旦把 `XComponent` 放进条件分支，旋转时它会被销毁重建，
surface id 变化，`av.surfaceId` 还指向旧 surface → 黑屏/冻结。

### 4.2 方向状态机（唯一真源）

```ts
@State winW: number = 0;          // vp
@State winH: number = 0;
@State safeTop: number = 0;
@State safeBottom: number = 0;
@State safeLeft: number = 0;      // 横屏挖孔在侧边
@State safeRight: number = 0;
@State streamAR: number = 16 / 9; // 宽/高，来自接口或 videoSizeChange
@State rotationInProgress: boolean = false;

private onRootArea = (o: Area, n: Area): void => {
  const w: number = n.width as number;
  const h: number = n.height as number;
  if (w <= 0 || h <= 0) return;
  if (Math.abs(w - this.winW) < 1 && Math.abs(h - this.winH) < 1) return;
  // onAreaChange 在布局阶段回调，延迟到本帧后改状态，避免「渲染中改状态」
  setTimeout(() => {
    const wasLandscape: boolean = this.isLandscape;
    this.winW = w;
    this.winH = h;
    this.isLandscape = w > h;
    this.refreshSafeArea();                 // 旋转后必须重读
    if (this.isLandscape !== wasLandscape) {
      this.onOrientationChanged();
    }
  }, 0);
};
```

`refreshSafeArea()`：

```ts
private refreshSafeArea(): void {
  if (!this.mw) return;
  const sys = this.mw.getWindowAvoidArea(window.AvoidAreaType.TYPE_SYSTEM);
  const nav = this.mw.getWindowAvoidArea(window.AvoidAreaType.TYPE_NAVIGATION_INDICATOR);
  this.safeTop = sys.topRect.height;
  this.safeLeft = sys.leftRect.width;
  this.safeRight = Math.max(sys.rightRect.width, this.notchRight());
  this.safeBottom = nav.bottomRect.height;
}
```

> 注意：`display.getDefaultDisplaySync()` 返回的是**物理屏**尺寸，分屏/折叠/自由窗口下不等于窗口尺寸。
> 全部改用根节点 `onAreaChange` 拿到的窗口内尺寸。

### 4.3 几何派生（替换 videoW/videoH）

```ts
/** 视频「显示矩形」：contain 模式，居中；cover 模式用于「裁剪」，fill 用于「拉伸」 */
private videoRect(): Rect {
  const W: number = this.winW;
  const H: number = this.winH;
  const ar: number = this.streamAR;

  if (this.isLandscape) {
    // 横屏：视频区 = 整窗（聊天面板是浮层，不挤压视频）
    return this.fitRect(0, 0, W, H, ar);
  }

  // 竖屏：先定视频区高度
  const areaTop: number = this.safeTop + 48;          // 顶栏 48
  const areaH: number = this.isPortraitStream()
    ? Math.min(H * 0.52, W / ar)                       // 9:16 源：限高 52%
    : W / ar;                                          // 16:9 源：整宽
  return this.fitRect(0, areaTop, W, areaH, ar);
}

private fitRect(x: number, y: number, w: number, h: number, ar: number): Rect {
  const scale: number = Math.min(w / (ar * 1000), h / 1000);
  const vw: number = ar * 1000 * scale;
  const vh: number = 1000 * scale;
  return { x: x + (w - vw) / 2, y: y + (h - vh) / 2, w: vw, h: vh };
}
```

- 比例按钮改为循环 `适应(contain) → 裁剪(cover) → 拉伸(fill)`，不再是 16:9/4:3/fill 的硬编码。
- `streamAR` 的三条来源优先级：
  1. `av.on('videoSizeChange')`（最准，切流/切画质都会回调）
  2. `LiveStreamUrlResult.videoWidth/videoHeight`（LiveApi.ets:121-128，起播前就能拿到）
  3. 兜底 16:9

```
├──────────────────────────────┤
│ 标题（1行省略）     英雄联盟 ▾ │  信息条 56vp
├──────────────────────────────┤

├──────────────────────────────┤

```

- 竖屏源（9:16）时视频区高度取 `min(52% * H, W/ar)`，两侧用 `roomCover` + `blur(40)` + 黑色 45% 遮罩补底，**不裁切画面**。
- 聊天列表用 `Scroll + Column`，不用 `List`（本项目已知：ListItem 交叉轴宽度无法收缩，见 AGENTS「ArkUI List 交叉轴宽度陷阱」）。
- 列表默认贴底；用户上滑后暂停自动滚动，右下角浮出「N 条新消息 ↓」胶囊，点击回底并恢复跟随。
- 消息渲染上限 200 条（`chatRenderCount`），超出裁剪最旧；旋转期间降到 60 条，旋转结束后分批 +20 恢复（照抄 VideoPlayerPage 的 `rotationInProgress` 做法）。

```
│            9:16 → 291×517 居中            │ 用户名：内容     │ 宽 280vp
```

- **聊天面板是浮层，不挤压视频**：16:9 视频在 831×517 窗口里本来就只有 467vp 高，再横向切掉 280vp 会变成 551×310，画面骤小。
  PiliPlus 也只在「非全屏横屏」才分栏（`view.dart:700` `isFullScreen ? maxWidth : videoWidth`）。
- 面板：`right: 12`、`top: safeTop+52`、`bottom: 64`、宽 `clamp(W*0.34, 260, 340)`、圆角 16、
  背景 `rgba(16,17,22,0.72)` + `backgroundBlurStyle(COMPONENT_THICK)`。
- 面板**默认收起**，点控制条右侧 💬 展开（默认展开会遮住约 1/3 画面）；展开后弹幕 Canvas 缩到面板左侧并重算轨道。
- 当前已落地版本：横屏底部改为**左右两个毛玻璃胶囊**（左：播放/刷新/比例/画质；右：旋转锁定/更多），中间留空露出画面；
  旋转锁定已从「更多」提到表面。
- 弹幕 Canvas 宽度 = 视频显示矩形宽度 −（面板展开时的面板宽度 + 12）。**弹幕不要飘到面板底下**。
- 竖屏源横屏看：视频 291×517 居中，两侧同样用封面模糊补底；面板仍浮在右侧。

### 4.6 旋转过渡（4 条路径统一处理）

```
竖→横 / 横→竖：
 ① onAreaChange 拿到新窗口尺寸（早于/伴随系统旋转）
 ② rotationInProgress = true
    · 聊天面板 opacity→0（180ms），但不卸载
    · LiveDanmakuController.pause()（停止 setTimeout 链，保留 buffer）
    · 聊天列表 renderCount 降到 60
 ③ 立即按新几何布局（视频槽只改 position/size，不重建 XComponent）
 ④ 系统旋转动画约 460ms（NotifyRotationAnimationEnd）
 ⑤ 480ms 后 rotationInProgress = false
    · danmaku.resize(newW,newH)：trackManager.initialize + clearTracks + 重新播种最近 15 条
    · 聊天面板淡入，renderCount 分批恢复到 200
 ⑥ 校验 surfaceId：若 xc.getXComponentSurfaceId() 与 av.surfaceId 不一致，补一次 av.surfaceId = sid
```

为什么必须播「最近 15 条」：`clearTracks()` 之后如果只等新消息，旋转后会有 1~3 秒的空屏，
观感像「弹幕被转没了」。用 buffer 里最后 15 条重新入轨，第一帧就有内容。

为什么聊天面板用 `opacity` 而不是 `if`：`if` 会卸载 Scroll 并丢失滚动位置。同理，
聊天列表在旋转期间不要重建，只降渲染条数。

### 4.7 弹幕链路（直播）

#### 4.7.1 数据获取

```http
GET https://api.live.bilibili.com/xlive/web-room/v1/index/getDanmuInfo?id={roomId}&type=0&web_location=444.8&w_rid=…&wts=…
→ data.token
→ data.host_list[{ host, wss_port, ws_port, port }]
```
需要 WBI 签名；本项目已有 `WbiSign.getWbiKeys()` + `WbiSign.sign()`（`utils/SignUtils.ets:161/208`）。

#### 4.7.2 WebSocket 协议（对齐 `PiliPlus/tcp/live.dart`）

- 地址：`wss://{host}:{wss_port}/sub`，host_list 逐个尝试。
- 16 字节大端包头：`totalSize(4) headerSize(2)=16 protoVer(2) op(4) seq(4)`。
- 认证包 `op=7`，body：
  `{"uid":<mid>,"roomid":<roomId>,"protover":1,"platform":"web","type":2,"key":"<token>"}`
  ⚠️ **protover 用 1，不要用 3**：protover=3 是 brotli，HarmonyOS 没有现成的 buffer 解压 API；
  protover=2 是 zlib，`@ohos.zlib` 只提供文件级接口，也不方便；protover=1 是**明文 JSON**，最稳。
- 心跳 `op=2`，每 30s 一次，`seq` 自增。
- 收包：`op=8` 认证成功（开始心跳）；`op=3` 心跳回复（忽略）；`op=5` 消息。
  op=5 的 body 可能是**多个子包首尾相连**，要按 `totalSize` 循环切分。
- 重连：`onclose/onerror` → 指数退避 1s/2s/4s/8s，最多 5 次；页面隐藏 30s 后可断开，回前台重连。

> ArkTS 用 `@kit.NetworkKit` 的 `webSocket`；`on('message')` 的 `value` 是 `ArrayBuffer`，
> 用 `new Uint8Array(value)` + `DataView` 解析。不需要额外权限（已有 INTERNET）。

#### 4.7.3 消息模型

```ts
export enum LiveMsgType { DANMAKU, GIFT, SUPER_CHAT, SYSTEM }

export class LiveMessage {
  id: string = '';
  type: LiveMsgType = LiveMsgType.DANMAKU;
  uid: number = 0;
  uname: string = '';
  text: string = '';
```

解析（兼容新老两种 `DANMU_MSG`）：

```
text   = info[1]

extra  = JSON.parse(info[0][15].extra)   // 新格式：{color, mode, id_str, emoticon, ...}
```

#### 4.7.4 渲染（复用现有渲染器）

新建 `services/LiveDanmakuController.ets`，**不要改 `DanmakuController`**（它和 cid/分段/时间轴强耦合）：

```ts
class LiveDanmakuController {
  private renderer: DanmakuRenderer;
  private tracks: DanmakuTrackManager;
  private clock: number = 0;          // 单调时钟（ms），页面打开即 0
  private visible: DanmakuItem[] = [];
  private buffer: LiveMessage[] = []; // 最近 30 条，旋转后重播
  private active: boolean = false;

  push(msg: LiveMessage): void {
    const item = new DanmakuItem({ content: msg.text, color: msg.color });
    item.time = this.clock;           // 立刻出现
    const track = this.tracks.assignTrack(item, this.clock);
    if (track < 0) return;            // 放不下就丢，不要留在列表里（已知坑）
    item.track = track;
    this.visible.push(item);
    this.buffer.push(msg);
    if (this.buffer.length > 30) this.buffer.shift();
  }

  // 16ms 自调度；异常必须 finally 继续调度（已知「渲染链静默中断」坑）
  private frame = (): void => {
    try {
      const dt = Math.min(200, Date.now() - this.last);
      this.clock += dt;
      this.renderer.render(this.visible, this.clock, dt);
      this.visible = this.visible.filter(i => i.visible);
    } catch (e) { logError(`[LiveDanmaku] ${e}`); }
    finally { if (this.active) this.timer = setTimeout(this.frame, 16); }
  };

  resize(w: number, h: number): void {
    this.renderer.setSize(w, h);
    this.tracks.initialize(w, h);     // 会清轨道
    this.visible = [];
    this.reseed();                    // 用 buffer 最后 15 条重新入轨
  }
}
```

要点：
- **限流**：单帧最多推 6 条；同一 uid 3 秒内相同内容去重；总量超过 120 条时丢弃新消息（保留现有）。
- **不合并同内容**：直播里「666」重复是真实信息，合并会失去热闹感；点播才需要合并。
- **Canvas 尺寸 = 视频显示矩形**，不是整窗。旋转/切面板时 `resize()`。
- 弹幕字号在横屏用一个 `fullScreenFontScale`（1.15），竖屏 1.0。

#### 4.7.5 发送弹幕

```http
POST https://api.live.bilibili.com/msg/send
form: roomid, msg, color=16777215, fontsize=25, pool=0, mode=1, rnd=<秒级时间戳>, csrf=<bili_jct>
```
- `bili_jct` 从 `AppStorage['biliCookie']` 解析；未登录时输入框置灰并提示。
- 频率限制：前端做 2s 冷却 + 每分钟 20 条上限，失败按服务端 `code` 提示（10030 频率过高、10031 被禁言等）。
- 发送成功后**本地先插一条**（`selfSend`），不要等服务端广播，否则自己的弹幕要 1~2s 后才出现。

### 4.8 评论（聊天）面板

- 数据源与弹幕**同一条 WS**，`LiveChatStore` 是唯一真源：
  - 弹幕层订阅 `DANMAKU`；
  - 聊天面板渲染全部类型（弹幕 / 礼物 / SC / 系统）。
- 渲染上限 200 条，`ForEach` + `Scroll`（不用 `List`）。
- 每条消息：`[粉丝牌] 用户名：内容`；礼物/SC 用带底色的独立行（SC 用渐变边条）。
- 自动滚动：`scrollTo({ y: max })`，用 80ms 节流；用户上滑超过 40vp 停止跟随。
- 新消息计数：停止跟随时累加，浮出「N 条新消息 ↓」。
- 输入栏：点击弹出系统键盘（`TextInput` + `focusControl`），发送后清空、收起键盘、回到底部。

### 4.9 直播特有：暂停/恢复

直播没有进度，暂停 30 秒再播，等于落后 30 秒。策略：

```
onPageHide（非后台播放）→ pause + 记录 pausedAt
onPageShow:
  if (now - pausedAt < 3s)  → av.play()                 // 短暂暂停，直接续
  else                      → releaseAVPlayer() + startPlay(true)  // 重新拉流，回到直播边缘
                              并 Toast「已回到直播」
```
`startPlay` 复用现成逻辑，但要注意 `videoSrc=''` 会导致 XComponent 被 `if` 卸载——
改造后视频槽常驻，`videoSrc` 变化只重建 XComponent 本身（可接受），不要在布局分支里。

| 项 | 措施 |

## 七、风险与已知坑

1. **XComponent 不能进条件分支**——本项目 AGENTS 已记录「常驻播放器层只改几何不改挂载」。
2. **`List` 交叉轴宽度无法收缩**——聊天列表用 `Scroll + Column`，别用 `List`。
3. **弹幕自调度链**——`setTimeout` 递归必须 `try/finally` 续链，存活标志不能用 timer id。
4. **`clearTracks()` 要清 `lastItem`**，否则重置后所有轨道被判满，弹幕全灭（已修，别回退）。
5. **protover 选 1**，避免 brotli/zlib 解压依赖；若日后要省流量再引入解压。
6. **WBI 签名**：`getDanmuInfo` 需要签名，直接复用 `WbiSign`，不要自己拼 `w_rid`。
7. **发送弹幕需要 csrf**：`bili_jct` 缺失时不要发请求，UI 直接提示登录。
8. **旋转期背景页重排**是系统行为，直播页只能降自身负载，不能阻止 HomePage 重排。

## 八、与点播播放器的关系

**不要直接复用 `VideoPlayerPage` 的整页布局**：它的全屏/竖屏横看/关灯/分集/进度条/续播逻辑对直播全部无意义，
且 12000+ 行、状态耦合深。只复用三样：

1. `onAreaChange → @State cw/ch` 的响应式尺寸链；
2. 「常驻播放器层只改几何」的挂载策略；
3. `rotationInProgress` 期间降载、结束后分批恢复的做法。

弹幕则复用 `DanmakuRenderer` + `DanmakuTrackManager`，**另写实时控制器**，不碰 `DanmakuController` 的分段/时间轴。
